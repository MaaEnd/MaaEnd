# IconRecognition 可信色带规则晶格设计

## 背景

`transfer` 与 `port_storager` 都使用 64px 物品格，但截图中的格框、物品纹理、稀有度条和界面背景会互相干扰。现有实现已经引入结构峰和稀有度条拟合，但仍存在两类系统性问题：

- 灰色或黄色背景接近某档稀有度颜色时，背景会被当成色带。
- 候选一旦选择了错误列数或相位，规则补全会把局部错误扩展成整片错位网格。

已确认的回归入口包括 `transfer` 的 1、25、100、106、108 等截图，以及 full 与独立 left/right 不一致的 4、41、53。截图编号只用于固定回归，不允许进入生产判断条件。

当前数据实际包含 rarity 1–6 共六档，不是五档。现有 `MeasureRarityRow` 会逐原型计算覆盖率，但随后仅保留“六色最大覆盖”和“非灰色最大覆盖”，过早丢失了每种颜色各自的证据。

## 目标

1. 使用六档稀有度颜色的独立证据判断每个候选色带是否可信。
2. 使用单一全局晶格描述每个左右子网格，禁止逐格累积误差。
3. 联合色带、格框边界和规则几何选择网格；证据冲突时低置信失败。
4. 保留当前结构检测能力作为有条件 fallback，不保留明显错误的输出。
5. 对现有 transfer 与 port_storager 全量样本进行无新增退化验证。
6. 将 manual runner 改为用例级并行，缩短全量验证时间，不改变生产识别行为。

## 非目标

- 不修改图标模板匹配阈值、模板资产或物品模型。
- 不在单张图片内部增加生产并行。
- 不根据截图编号、固定物品或单个失败坐标添加特例。
- 不允许每个相邻格子独立选择 68、69 或 70px 间距。
- 不要求同一行或同一列的物品具有相同稀有度。

## 证据依据

### 网格间距

完整 transfer 基线报告中：

- 横向 1218 个相邻间距有 1216 个为 69px。
- 纵向 653 个相邻间距有 642 个为 69px。

直接扫描 112 张 transfer 截图的彩色色带峰时，相邻可靠峰只出现 68/69px。port_storager 的 10 张截图也以 68/69px 为主，个别 67px 是相邻色带端点各有 1px 量化误差后的观测值。

因此 69.0px 作为 720p UI 的先验中心有数据支持，但不能作为每张图的强制结果。

### 当前性能基线

manual runner 当前按用例串行运行。本机为 24 个物理核心、32 个逻辑处理器、约 96GB 内存。transfer 的 336 个 full/left/right 用例约需两小时，适合在测试工具层进行并行。

## 总体架构

处理流程分为六层：

1. 结构候选召回。
2. 六色逐格证据计算。
3. 局部背景对比与色带可信度计算。
4. 全局规则晶格拟合。
5. 联合评分与有条件 fallback。
6. 低置信失败与诊断输出。

每层只产生证据或候选，不在证据不足时直接补出完整网格。

## 六色逐格证据

`RarityRowEvidence` 不再只返回两个最大值，而是保留六档原型各自的覆盖率。每个候选格底部的每一行都得到六维覆盖向量。

对每个颜色通道计算：

- 与该 rarity Lab 原型的覆盖率。
- 与候选色带上、下局部背景的 Lab 色差。
- 水平连续长度和覆盖比例。
- 窄条的上、下边缘响应。
- 色带厚度是否位于稳定范围。

颜色接近但局部背景对比不足时，只能得到低可信度。例如黄色背景中的黄色像素块即使接近黄色原型，只要与上下背景色差低、缺少窄条边缘，就不能作为可靠色带。

rarity 1 灰色作为独立通道保留，但不能单独生成网格。灰色证据只有在结构边界已经支持候选时才加分，以减少灰色背景误检。

同一行可以由不同颜色的格子共同支持。联合拟合使用每个格子的最佳可信颜色，不要求整行颜色一致。

## 全局规则晶格

每个左右子网格分别拟合一个全局模型：

```text
x(i) = round(origin_x + i * pitch_x)
y(j) = round(origin_y + j * pitch_y)
```

其中 `origin_x/origin_y/pitch_x/pitch_y` 在一次候选拟合中保持不变。`pitch_x` 与 `pitch_y` 使用浮点数，69.0px 是先验中心，68–70px 是候选搜索范围。

所有观测格框和可信色带底边都投影到同一模型，并计算残差。相邻整数坐标可能因统一浮点 pitch 的舍入自然呈现 68/69 或 69/70，但禁止逐格选择不同间距，也禁止用前一格坐标递增生成下一格。

候选出现以下情况时直接淘汰：

- 残差随行号或列号持续增长。
- 需要分段 pitch 或逐格改变间距才能解释。
- 大量预测格没有格框或可信色带支持。
- 左上起序与界面方向不一致。

只有单行或单列、无法独立估算 pitch 时，才使用 69.0px 先验，并降低几何置信度。

## 结构候选与方向

当前涉及的 transfer 与 port_storager 子网格都从左上方开始，先向右排列，再换行。结构召回继续使用现有格框边界、投影峰和左右区域划分，但候选必须显式携带：

- 可见的格框边界对。
- 观测到的行列索引。
- 全局 origin 与 pitch。
- 每个观测点的残差。
- 未被解释的强结构数量。

不能因为某个候选列数更多就直接获胜。单卡片稀疏场景只保留直接观测到的格子，不能从一个格子向远处补出整片网格。

## 联合评分

每个候选分别计算三组归一化分数：

### 结构分

- 可见格框边界对数量。
- 边界方向和完整性。
- 左上起序一致性。
- 全局 pitch 与观测边界残差。

### 色带分

- 每格最佳 rarity 通道的可信度。
- 色带与局部背景的对比度。
- 水平连续性、边缘和厚度。
- 完整色带格数量。

### 一致性分

- 色带底边与全局晶格的残差。
- 格框与色带是否指向同一 origin/pitch。
- 候选是否解释了画面中的可信色带和强结构。
- 预测但无证据的格子比例。

评分用于比较已经通过硬约束的候选，不替代硬约束。第一名与第二名差距过小时，视为低置信，不强行选择。

具体权重不得按单张截图手调；应通过真实回归、黄色/灰色背景合成干扰和全量数据共同校准。

## 有条件结构 fallback

当前结构检测作为 fallback 候选来源保留，但仅在以下条件同时成立时采用：

- 格框边界清晰且数量足够。
- 全局 pitch 稳定，无累积残差。
- 左上起序和可见范围合法。
- 没有可信色带与其冲突。
- 预测格中有足够比例获得直接结构支持。

色带证据不足但结构很强时可以输出。结构也不足或与色带冲突时，返回低置信失败。

`transfer/25.png` 是 fallback 边界回归：左侧只有一个真实卡片，当前错误候选位于右下背景。新模型应保留直接观测到的左上卡片，拒绝远端假两列，不能依赖截图编号。

## 失败与诊断

对外不扩大 `DetectGrid` 的调用接口。内部候选携带置信度和拒绝原因；没有合格候选时沿用现有异常到 `RecognitionResult.error` 的转换，manual runner 将该用例标为失败。

诊断至少记录：

- 最佳和次佳候选总分及差值。
- origin、浮点 pitch、行列数。
- 结构分、色带分、一致性分。
- 全局最大残差和残差趋势。
- 六色可信格数量。
- fallback 是否启用及启用原因。
- 候选淘汰原因。

## Manual Runner 并行设计

并行只发生在测试工具的不同 `ManualRunnerCase` 之间。单张图片的生产识别路径保持不变。

### 接口

- C++ runner 新增 `--jobs <N|auto>`。
- PowerShell 新增 `-Jobs <N>` 并透传。
- `run-tests.local.psd1` 与示例允许配置 `Jobs`。
- 显式命令行参数优先于本机配置。

`auto` 根据物理核心数选择，最大不超过 16。本机目标值为 16，同时保留显式 1/4/8/12/16。

### 执行模型

- 在主线程预热并冻结模板缓存。
- 固定大小 worker pool 通过原子索引领取 case。
- `IconRecognizer` 只共享初始化后的只读模板；每个 case 的图片、请求、结果和诊断独立。
- annotated/detail 文件名按 case 唯一，worker 可独立写入。
- 报告先写入与 case 索引一致的结果槽，最后由主线程按原顺序输出。
- worker 捕获单 case 异常并记录，不因一个失败中断其他用例。

当 `jobs > 1` 时，在 runner 进程内限制 OpenCV 内部线程，避免 worker 数与 OpenCV 内部线程相乘导致过度并发。该设置仅影响 manual runner。

### 并行基准

使用固定代表样本分别运行 1/4/8/12/16 workers，并验证：

- detail JSON 的语义内容一致。
- annotated 图片和匹配结果一致。
- case 顺序和文件命名稳定。
- 无数据竞争或偶发失败。
- 记录总耗时、cases/s 和峰值内存。

选择实测最快且稳定的 worker 数；如果 16 优于 8，则本机默认使用 16。目标是将 transfer 全量从约两小时降低到 10–20 分钟，最终以基准结果为准。

## 测试策略

### 单元与真实回归

- 六维 rarity 覆盖向量。
- 灰色、黄色背景与同色真实窄条的局部对比。
- 混合 rarity 的同一行可以共同支持晶格。
- 全局浮点 pitch 的整数投影无累积偏差。
- 逐格可变 pitch 候选被拒绝。
- 稀疏单卡只保留直接观测格。
- 现有 1、25、100、106、108、4、41、53 等真实 fixture。
- 当前 port_storager/1 的左右不同 origin。

### 合成干扰

- 灰色背景接近 rarity 1。
- 黄色背景接近黄色 rarity。
- 跨格裁剪形成约 0.9 覆盖的假色带。
- 顶部工具栏伪色与真实晶格近似同周期。
- 首末行遮挡、空格和单行/单列。

### 全量验收

- transfer 112 张图片的 full/left/right 共 336 个用例。
- port_storager 10 张图片的全部可用 ROI。
- full cell 集合必须等于独立 left + right。
- 每个子网格只有一个全局 origin/pitch，且残差不累积。
- 已正确识别的真实物品不得丢失。
- 任何匹配下降立即停止并转成回归调查。
- 任何新增大范围错位网格均视为失败。
- 低置信失败优于输出明显错位网格。

## 实施顺序与 Git 检查点

1. 将本设计文档纳入当前工作树。
2. 创建完整 WIP 检查点提交，包含当前 IconRecognition 算法、测试、文档、测试工具和故意失败的 `transfer 25` RED。
3. 先实现 manual runner 用例级并行并验证输出一致性。
4. 按 TDD 扩展六色证据和局部可信度。
5. 实现全局浮点晶格与联合评分。
6. 接入有条件结构 fallback 和诊断。
7. 运行单元、真实、合成与全量验收。

检查点是可恢复基线，不代表算法已完成或全量测试已通过。后续实现失败时可回到该提交，不通过重置或覆盖用户已有改动来恢复。
