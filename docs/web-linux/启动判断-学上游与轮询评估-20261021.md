# 启动判断：该不该自己轮询？—— 学上游的做法 · 2026-10-21

## 1. 问题回顾

`run_daily_linux.py` 原先在开跑前用 `needs_start()` 抓**一帧**画面，判断页面是不是还停在启动页/标题页：

```python
ctrl.post_screencap().wait()
img = ctrl.cached_image
for node in ('WebLauncherStartButton', 'WebTitleContinue'):
    ... 命中才 return True
return False
```

00:25 那次整轮空跑（4 个 20 s 超时全是 `SceneAnyEnterWorld`）就是因为它：页面刚导航到 `/cloud`，
「开始游戏」按钮还没渲染出来 → 判成「已经在游戏里」→ 跳过启动 → 任务对着启动页跑。

我当时的补丁是把它改成**轮询 30 秒**。用户的疑问是对的：真的要这样吗？先看上游。

## 2. 上游是怎么做的

| 项目 | 做法 | 关键点 |
|---|---|---|
| MaaEnd `LaunchGamePC` | **pretask**（`{"pretask": {... "exec":"agent/go-service", "args":["--pretask","LaunchGamePC"]}}`） | 「启动」是独立阶段，由 agent 执行，不塞进每个任务 |
| MaaEnd `AndroidOpenGame` | `task` + `StartApp` 动作 + `pipeline_override` | 平台差异（包名）用覆盖解决，不用脚本判断 |
| MaaFramework 节点语义 | 节点自带 `timeout`（识别重试窗口）、`next` 按顺序试到命中、`max_hit`、`pre/post_wait_freezes` | **等待/重试是框架的事**，不是调用方的 `while` 循环 |
| 我们的 `WebStartGameEntry` | `DirectHit` + `timeout: 600000` + `next=[WebSessionBusy, WebMonthlyCard, **WebAlreadyInGame**, WebTitleContinue, WebQueueDetected, WebLauncherStartButton]` | 已经是上游那个形状：命中哪个分支就走哪条路 |

其中 `WebAlreadyInGame` = `Or[InWorld, InMenuList]` → `DoNothing`：**已经在游戏里就命中即结束**。
也就是说，「要不要点开始游戏」这件事，节点自己就能回答。

## 3. 三种方案对比

| 方案 | 在启动页 | 已在游戏里 | 页面还没渲染完 | 评价 |
|---|---|---|---|---|
| 单帧判断（原实现） | 命中→启动 | 需命中 InWorld/InMenuList | **漏判 → 整轮空跑** | ✗ 已实测出错 |
| 轮询 30 s（我的补丁） | 命中→启动 | **白等最多 30 s** 才返回"不用启动" | 能兜住 | △ 治标，且给正常路径加成本 |
| **直接跑 `WebStartGameEntry`（现方案）** | 点开始 → 等进游戏 | `WebAlreadyInGame` 命中即结束（约 1–2 s，未实测） | 节点 600 s 窗口内持续重试 | ✓ 与上游一致 |

## 4. 结论

- **不需要**自己写轮询：`timeout` 就是框架的重试窗口，`next` 就是分支决策，二者组合已经覆盖「慢渲染 / 排队 / 已在游戏」；
- 30 s 轮询的真正问题是**把成本加到了正常路径上**（已经在游戏里也要等满 30 s 才敢返回），
  而它修的只是「单帧判断」这个不该存在的判据；
- 已改为：开跑前**无条件**跑一次 `WebStartGameEntry`，失败才硬重置。`needs_start()` 整段删除（26 行）。

## 6. 遗留

- `WebAlreadyInGame` 的「秒过」路径没有实测（日常流程每次都会重启浏览器，必然从启动页开始）。
  如果哪天改成复用浏览器/会话续连，这一条会真正派上用场，届时测一次即可。
