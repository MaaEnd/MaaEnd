# 分析报告：稳定物资「跑了但一件没买」的根因

日期：2026-10-20 · homesrv · 结论已用实跑验证（6 次购买成功）

---

## 1. 现象

`AutoStockStaple`（自动购买稳定需求物资）每天在跑、任务返回 OK，但**商店里什么都没买**：

- 进入谷地/武陵的稳定物资界面 ✅
- 把商品列表从头滑到尾（`AutoStockSwipeValleyIV` 8 次、`Wuling` 18 次）✅
- 购买节点 `AutoStockBuyItemValleyIVTask` **9 次尝试 / 0 命中**，`Wuling` **19 次 / 0 命中** ❌
- 最后 `AutoStockStapleDone` 正常结束，日志显示 `succeeded=True`

---

## 2. 排查路径（先排除的三件事）

| 怀疑对象 | 证据 | 结论 |
|---|---|---|
| 画质/云串流太糊 | OCR 读到「新锐谷地探物器」**score 0.9998**、「新锐谷地罗盘」0.9999 | ❌ 不是画质 |
| 颜色参数（云编码色偏） | 抄了云层 13 个颜色节点后，`AutoStockInStapleItem` 从「整行认不出」变成命中 box `[71,180,55,18]` | ✅ 修好了一环，但仍不买 |
| 没货/售罄 | 界面 OCR 有「库存10 / 库存40 / 库存30」；`SoldOut` 在修复前 0 命中 | ❌ 不是没货 |
| 上游没这个功能 | `tasks/AutoStockStaple.json` + 60 多个 `AutoStockStapleGoods*` 节点齐全 | ❌ 不是缺功能 |

**关键异常**：`AutoStockInStapleItemName`（商品名 OCR）**78 次结果、0 次命中**，但它读到的文本和分数都是对的。

---

## 3. 根因：`resolve_preset.py` 没有把「要买什么」传进任务

### 3.1 机制

MXU 在 GUI 里提交任务时，会把任务的 `optionValues` 按 `option.cases[].pipeline_override` 展开成一个覆盖字典。稳定物资的购买清单是这样传的（`tasks/AutoStockStaple.json`）：

```json
"AutoStockBuyDailyGoodsValleyIVItems": {
  "type": "checkbox",
  "cases": [
    {"name": "KeenValleyDetector",
     "pipeline_override": {
       "AutoStockInStapleItemName": {
         "attach": {"keen_valley_detector": ["新锐谷地探物器", "新銳谷地探測器", "Keen Valley Detector", …]}
       }}}
  ]
}
```

运行时由 go-service 的 `AttachToExpectedRegexAction` 把 `attach` 里的名字注入 `AutoStockInStapleItemName.expected`，OCR 才有东西可比对。

### 3.2 我们的解析器只展开两层

旧 `resolve_task()` 的逻辑：

- 第一层：遍历 `task.option`，合并选中 case 的 `pipeline_override`；
- 第二层：只处理 `case.option` 里的**直接子选项**，合并它们的 `pipeline_override`；
- **第三层及以下：只 `seen.add(sub)`，从不处理**。

而稳定物资的选项链是 **四层**：

```
AutoStockStaple
└─ AutoStockStapleValleyIV (1)
   └─ AutoStockBuyDailyGoodsValleyIV (2)
      └─ AutoStockBuyDailyGoodsValleyIVItems (3)   ← 购买清单在这里
         └─ case KeenValleyDetector (4)
```

所以 `AutoStockInStapleItemName.attach` **从来没有被合并**。

### 3.3 第二个缺陷：`input` 型选项被完全忽略

`AutoStockReserveValleyIV`（库存保留阈值）这类选项的 `pipeline_override` **直接挂在 option 根上**（不在 case 里），用 `{ReserveValleyIV}` 占位。旧解析器只找 `case.pipeline_override`，于是：

- `AutoStockTargetCompareValleyIV`（判断"库存够不够，要不要买"）也没被覆盖 → 即使有清单，判断也用默认值。

### 3.4 证据（同一份预设，新旧解析器对比）

| 任务 | 旧覆盖项 | 新覆盖项 |
|---|---|---|
| AutoStockStaple | **5** | **88** |
| CreditShoppingN2 | 21 | 26 |
| DailyRewards | 11 | 15 |

AutoStockStaple 原来只拿到 5 个覆盖（`ScheduleEnabled`、`ValleyIV/Wuling` 开关、两个折扣阈值），**购买清单 0 条，各项 `Validate` 节点 0 个**。

---

## 4. 修复

重写 `resolve_task()` 的展开逻辑（`web/linux/resolve_preset.py`）：

1. **真正递归**：`walk_option()` 一路下钻 `case.option`，深度上限 12；
2. **支持 input 型**：从 option 根合并 `pipeline_override`，并把 `{InputName}` 替换成 `optionValues[opt].values[name]`；
3. 保留原有 `$value` 替换与 `deep_merge`（dict 递归、list 整体替换）。

备份：`resolve_preset.py.bak-20261020-215455`

---

## 6. 影响面与后续

1. **不只是稳定物资**：`CreditShoppingN2`（+5 覆盖）、`DailyRewards`（+4）也一直少传选项。修复后建议各跑一次确认行为变化（尤其信用店购买过滤）。
2. **建议加一条基线**：每次改动后打印每个任务的 `n_override` 与关键 `attach` 条目数，掉到 0 就说明解析器又漏了。
3. 颜色 A′ **仍然要保留**：它修的是「商品行锚点」，是另一环；没有它，即使有清单也定位不到商品行。
4. 这个 bug 与上游无关、与云画质无关，是**我们自己的 headless 运行器**的问题——`resolve_preset.py` 的注释里本来就写了"复现 MXU 的行为"，但只复现了两层。
