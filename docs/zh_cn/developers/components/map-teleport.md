# 开发手册 - MapTeleport 大地图传送

MapTeleport 是基于原生 C++ 实现的大地图传送点点击系统。节点只需给出「哪个区域、区域底图上的哪个坐标」，它自己算出这个坐标当前落在屏幕的什么位置，确认那里确实有传送图标，再点下去。

它与 [MapLocator](./map-locator.md) 共用同一套模板匹配内核和同一批区域底图。区别在于 MapLocator 看的是小地图、回答「角色在哪」，MapTeleport 看的是全屏大地图、回答「这个坐标现在画在屏幕哪」。

- [MapTeleportSelect](#mapteleportselect)
- [两类传送点](#两类传送点)
- [新增传送点](#新增传送点)
- [识别原理](#识别原理)

MapTeleport 属于 Action 层，只负责在已经打开的大地图上点中传送图标。打开地图、切图层、调缩放由 [SceneManager](../scene-manager.md) 的万能跳转负责，点完之后的确认弹窗也由 Pipeline 接管。

## MapTeleportSelect

在当前大地图画面上找到指定传送点并点击。

节点执行时会自行截图、求解视口、必要时拖动地图，直到目标进入可点区域并确认到图标为止。**确认不到图标就不点**——算得出坐标不等于那里有东西，宁可返回失败让上层重试或走 `on_error`，也不按算出来的坐标空点。

### 节点参数

必填参数（`custom_action_param`）：

| 参数 | 说明 |
| -------- | ------------------------------------------------------------------------ |
| `zone` | 区域名，即 `assets/resource/image/MapLocator/` 下的目录名，如 `Wuling` |
| `target` | 2 个数字的数组 `[x, y]`，该区域底图像素坐标系下的传送点位置 |

区域底图是整个区域拼成的一张大图，区域内各子区域在它上面各占一块互不重叠的位置，`target` 用的就是这张大图的坐标——所以子区域不是参数，也不需要是参数。把地图切到含有该点的子区域，是入口链上 `all_of` 识别闸的职责，本 Action 以此为前提执行：闸不通过节点就不会运行。

可选参数（`custom_action_param`）：

| 参数 | 默认值 | 说明 |
| -------------- | ------ | ------------------------------------------------------------------------------------ |
| `core` | `false` | 该点是区域的基建传送点。切换到基建图标模板，并把 `target` 当作浮动范围的中心而非图标本身 |
| `max_attempts` | `4` | 识别尝试次数。拖动地图不计入 |
| `gate_base` | `10.0` | 命中与期望位置的偏差上限，单位底图像素。仅对普通锚点生效 |

### 成功与失败

| 结果 | 何时发生 |
| ------ | ------------------------------------------------------------ |
| 成功 | 确认到图标并点击成功；或角色已经站在该传送点上（见下） |
| 失败 | 视口求解不出、图标确认不到、拖动到地图边界仍够不着、传送点未解锁 |

角色自己的标记画在传送点图标之上，这会让图标认不出来——而它被盖住的原因恰恰是角色已经站在那了。这种情况下节点退出大地图并返回**成功**，剩下的距离交给 [MapNavigator](./map-navigator.md) 走过去。

传送点未解锁时返回**失败**，且不再重试——这是规则限制，重试多少次都一样。日志会明确写「未解锁」而不是「没认出来」，Pipeline 侧可以用 `on_error` 把这种情况路由到提示节点。

### 示例

普通传送锚点：

```json
{
    "MyTeleportTask": {
        "action": "Custom",
        "custom_action": "MapTeleportSelect",
        "custom_action_param": {
            "zone": "ValleyIV",
            "target": [
                452.3,
                910.8
            ]
        }
    }
}
```

基建传送点：

```json
{
    "MyBaseTeleportTask": {
        "action": "Custom",
        "custom_action": "MapTeleportSelect",
        "custom_action_param": {
            "zone": "Wuling",
            "target": [
                636.2,
                1319.2
            ],
            "core": true
        }
    }
}
```

## 两类传送点

**普通锚点**：位置固定，`target` 就是图标本身的坐标。确认时在期望位置的小窗内匹配锚点模板，命中点与期望位置相差超过 `gate_base` 底图像素就判为认错、不点。同一区域内两个传送点最近相隔 23.5 底图像素，默认的 10 像素闸留出了两倍余量。

**基建传送点**：目前 Pipeline 里的基建传送点仍走 SceneManager 的传统模板匹配实现，本节描述的是 `core` 这项已就绪、但尚未接线的能力。

图标画在玩家自己摆放的基建上，位置随摆放浮动，`target` 只圈得住范围、圈不准点位。此时 `target` 是浮动范围的中心，节点在这个范围里搜图标并以搜到的位置为准，因此 `gate_base` 对它无意义。一个区域最多一个基建传送点，图标只有两种样式，模板都在 `assets/resource/image/SceneManager/` 下，两张都试、取分高的那张。

基建传送点还多一道解锁判定。未解锁的基建不接受传送，节点会在确认到图标之后、点击之前把它拦下来。

> [!WARNING]
>
> 解锁判定的阈值只在已解锁的实拍上标定过。作者手头没有未解锁的账号，拿不到实拍，**未解锁那一侧至今没有验证过**。它不影响已解锁传送点的正常流程——只有在图标已确认、且金色比例掉到闸下时才会走到这一支。有条件的开发者请补测，确认后删掉本节警告与代码里的 `TODO`。

## 新增传送点

传送点节点写在 `assets/resource/pipeline/SceneManager/SceneTeleport<区域>.json`，填进 `__ScenePrivateMapTeleportPickAnchor` 槽位；入口节点写在 `Interface/Scene<区域>.json`，绑定该槽位并经由 `__ScenePrivateMap<子区域>EnterWorldAnchorWithPick` 进入——后者负责把地图切到主图层并调到非极端缩放。

缩放这一步不能省：缩放条推到两端时，参与视口求解的那块画面里地形太少，解不出唯一的视口。

加完新点后建议复核三件事：每个 `MapTeleportSelect` 节点有且仅有一个入口节点绑定它、它的 `all_of` 识别与所经的 `...EnterWorldAnchorWithPick` 节点一致、`target` 落在该区域底图范围内。

第二条尤其要紧：`all_of` 是子区域的唯一保证。写成了别的子区域，视口照样求解得出来（底图上两个子区域都在），只是目标落在画面之外很远的地方，节点会一路拖到地图边界才判失败——不会点错，但要空耗十几秒。

## 识别原理

本节面向需要了解内部实现的读者，日常使用可跳过。

整套判定分两级，两级回答的是不同的问题，且只有第二级决定点在哪：

1. **视口求解——镜头正对着哪**：取屏幕中央固定一块（避开左侧图层列表、右侧详情面板和上下栏），拿去和该区域的底图做多尺度模板匹配，解出屏幕与底图之间的相似变换 `base = (screen - roiOrigin) * scale + baseOrigin`。它决定的是**往哪看**，不是点哪。尺度扫描分粗解和细解两轮：粗解在降采样图上按等比阶梯扫全带，细解回到原分辨率只扫粗解胜出档位的邻域。
2. **图标确认——那里到底有没有图标**：把 `target` 经上一步的变换折算到屏幕，在这个位置的小窗内匹配图标模板，点击用的是匹配到的图标中心。

地图图标按固定屏幕尺寸绘制，不随地图缩放变——最佳匹配尺度恒为 1.000，偏离 5% 分数就掉到 0.6 以下。所以图标模板按采集分辨率下的显示尺寸出货，尺度阶梯必须正好踩得到 1.000。

截图由框架统一缩到同一个基准分辨率，但同一个图标在各端界面里画得并不一样大，移动端要比桌面端大出约四分之一。所以模板路径按控制器所加载的那几层资源依次解析，控制器自己那层排在基础层之前，与 Pipeline 里 `TemplateMatch` 用的是同一套层次——两端的模板于是各自都落在 1.000 附近，尺度阶梯不必为哪一端放宽。区域底图只有基础层一份，自然落到那里。日志会写出实际读到的那一份，层次不对一眼就能看出来。

模板的 alpha 通道当权重掩膜用：图标外圈那层柔和光晕在实拍里透着地形，让它参与相关只会拉低分数；基建卡片上的等级文字也一并挖掉，那块逐玩家不同。

目标落在可点区域外时，节点拖动地图而不是硬点。拖动单独记账、不计入 `max_attempts`——把目标挪进画面是这一步该干的事，不算识别失败。但每次拖动必须实打实缩短剩余距离，否则地图已经拖到边界，再拖也不动，此时立刻收手而不是空转。

解锁判定单独一路。已解锁与未解锁的图标只有颜色差别、形状一致，而灰度上的归一化相关对整体明暗不敏感，天生判不出来——这正是它认图标认得稳的原因。所以解锁与否改看颜色：模板自身哪些像素是金的，就去实拍的同一批像素上量还金不金。这一项只判解锁，绝不参与判真假——地图纹理自己就能达到很高的金色比例，它不能作为「这里确实有图标」的证据。

> [!IMPORTANT]
>
> 图标确认是点击的唯一依据。视口求解成功**不足以**支持点击——变换算得再准，也只说明「如果那里有图标，它应该在这个位置」，不说明那里真有图标。漏点一次的代价是重试一轮，点错一次的代价是点到别的传送点或空地形，两者不对等。
