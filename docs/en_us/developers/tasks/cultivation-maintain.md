# Development Manual - Cultivation Maintenance Documentation

This document explains the file layout, the reading flow and the Protocol Space integration of `Cultivation` (operator cultivation).  
This documentation was last updated on October 20, 2026.

It has only been verified on a real device with CloudADB (Cloud Endfield), official server, Simplified Chinese. For PC, see [To do: PC support](#to-do-pc-support).

## File paths

| Path | Purpose |
| --- | --- |
| `assets/interface.json` | Task registration (`other_menu` group) |
| `assets/tasks/Cultivation.json` | Six task entries and their options (generated) |
| `assets/resource/pipeline/Cultivation/Cultivation.json` | Open the overview, select the operator, switch the cultivation goal, page through four tabs (generated) |
| `assets/resource/image/Cultivation/Operators/` | PC operator portrait templates (generated) |
| `assets/resource_adb/image/Cultivation/Operators/` | ADB / CloudADB operator portrait templates (generated) |
| `agent/go-service/cultivation/` | Page parsing, need merging, plan storage, Protocol Space dispatch |
| `agent/go-service/cultivation/core/` | Pure logic without MaaFramework, with unit tests |
| `tools/Cultivation/build_resources.py` | Generates the tasks, Pipeline, locales in five languages and Custom Schemas |
| `tools/Cultivation/build_operator_templates.py` | Generates portrait templates for both sides from the CharIcon sources |
| `tools/Cultivation/calibrate_operator_scale.py` | Calibrates the portrait scale from screenshots of a new platform |
| `tests/Cultivation/test_overview.json` | Node tests for the overview entry and the cultivation goal |

The tasks, Pipeline and locales are generated by `build_resources.py`; do not edit the generated files by hand. After changing the generator, run:

```bash
python tools/Cultivation/build_resources.py
pnpm format
```

## Tasks

| Task | Purpose |
| --- | --- |
| Read cultivation needs | Opens the overview, selects the operator and goal, reads the four tabs twice and saves the plan |
| Cultivation task progress | Shows owned / required / gap, the source module and the essence status |
| Farm Protocol Space for the cultivation plan | Runs upstream Protocol Space (target inventory mode) with the plan's goals; **consumes sanity** |
| Export module integration preview | Writes `debug/record/CultivationModules.preview.json`; runs nothing |
| Clear cultivation needs | Deletes the plan and invalidates an in-flight older scan |
| I completed cultivation in game (manual confirmation) | Records the user's confirmation; a new scan clears it |

## Reading flow

1. `CultivationScan` reaches the operator page from any screen through `SceneEnterMenuOperator`, then clicks 「培养总览」 at the top right.
2. Select the operator (option `CultivationOperator`; "Current" skips this):
    - First match portrait templates from the top of the list, click, and confirm the header name with OCR.
    - If no portrait matches (skins, operators newer than the templates), fall back: `CultivationNextCard` finds cards by the rarity bar at their bottom and clicks them one by one, reading the header, until the name matches or the list ends. The fallback is slow (about 15 minutes in testing).
3. Switch the cultivation goal (option `CultivationExpectation`, default 卓越): continue if the header already shows the chosen goal; otherwise open the panel, click the chosen level and confirm the header again. If it cannot be confirmed, the task reports an error and reads nothing. Switching changes the operator's goal setting in game and consumes nothing.
4. Read the four tabs 「干员等级 / 技能与天赋 / 武器等级 / 武器基质」, twice in full. The plan is saved only when both passes agree; otherwise the previous plan is kept.

### Reading rules

- Only whole rows are read: a row at the bottom edge is kept or dropped as a whole, and on scrolled pages the faded top row is skipped (the previous page read it whole).
- Pages scroll with a 120 px swipe. On CloudADB the list scrolls about 1.6x the finger distance, and the earlier 240 px left whole rows between two pages.
- Items merge by their stable `IconRecognition` ID; needs of the same item in several sections add up, and inventory is counted once.
- Substitute boxes are skipped and not counted as needs.
- Items whose icon is not in the `IconRecognition` catalog are kept as "uncatalogued items" and saved to `debug/cultivation/`; reading continues.
- A tab that says 「已达上限」 or 「已满级」 needs nothing; if all four do, the plan is empty and the user is told nothing is needed.
- The weapon tab is split into sections by weapon name. An operator equips one weapon, and the option `CultivationWeapon` chooses which one counts.
- The essence tab reads only each weapon's flawless (gold) essence count. The essence need is met when the injected essence shows 「完全适配」 or a flawless essence with matching traits is owned; an injected essence with other traits does not count.

## Protocol Space integration

`CultivationFarm` does not copy the Protocol Space flow; it runs upstream `ProtocolSpaceSchedule` with `ctx.RunTask`:

1. Take the defaults of every option of the upstream `ProtocolSpace` task (including shared options such as those of `AutoFightSetting` defined in other task files) and deep-merge them as the client does (for example, the weekday checkboxes add up their `attach`).
2. Force `ProtocolSpaceMode = TargetInventory` and render the plan's needs into the 16 goals of `SupplyPlanLimits`; goals not involved are explicitly 0.
3. Replace `SupplyPlanAllTargetsMet` with a positive inventory comparison, so "no matching gap" is not taken as success.
4. The claim mode and the low-sanity behaviour come from this task's two options; the defaults are single claim and end the task (no sanity medicine).

SupplyPlan syncs the depot, picks the stage of the first gap, and repeats until every goal is met or sanity runs out. Afterwards the plan's "owned" numbers are still those of the scan; run "Read cultivation needs" again to see the latest progress.

Collection and essence are not dispatched yet; the preview only lists their goals and blockers, because the upstream target inventory modes of AutoCollect and AutoEssence do not support CloudADB yet.

## Adding operators

Operator options and portrait templates come from `tools/zmdmap/data/sell_product.json`:

```bash
uv run python -m tools.Cultivation.build_operator_templates
python tools/Cultivation/build_resources.py
```

The first command only adds missing templates for both sides; the second generates one option per operator. This is not wired into `sync-zmdmap.yml` yet, so run them after syncing zmdmap. If a portrait fails to match, the fallback still finds the operator, only slower.

## Known limits

- Official server, Simplified Chinese and a single account only; the plan holds one operator, and a new scan replaces it.
- A full read takes about 6–9 minutes depending on the number of rows; the fallback operator search adds more.
- "Automatically verified complete" is not implemented; completion only comes from the user's manual confirmation.
